# Часовой отчёт в Office dashboard

Страница `/office/hourly` использует существующую owner cookie авторизацию
дашборда. Она вычисляется из Room PostgreSQL при загрузке и автоматически
перезагружается каждые пять минут. Нового токена, публичного API, таблицы или
фоновой записи нет.

Единица учёта — `(room, task_id)`. Пять видимых категорий и скрытая шестая
«Готово» образуют ровно шесть пользовательских статусов. `done` остаётся в
базе, но не попадает в видимые карточки, показатели и события часа.
`cancelled` показывается отдельно как «Отменена» с сохранённой причиной и
ссылкой на историю, но не входит в активный WIP и не возобновляется страницей.
Живая аренда нужна, чтобы назвать карточку «В работе»; `open` не считается
исполнением. Открытый вопрос или backend `blocked` показывается как «Блокер»,
Событие `review` и ожидающий подтверждения ответ — «На проверке»; `paused`
остаётся в очереди с явной пометкой подтверждённой паузы. Срок свежести
результата показывается отдельно и не создаёт шестой статус.

Часовая дельта включает только события выделенного метода `room_task_progress`
с текстом результата, созданные в точном интервале `[as_of - 1h, as_of]` для
видимых незакрытых задач. Признак метода — `next_checkpoint_seconds` в audit
data. Общий `room_task_update` тоже пишет `progress`, но может означать лишь
заметку или смену статуса и поэтому не попадает в результаты часа.
`metadata_updated`, `claimed`, `heartbeat` и изменение `updated_at` не
являются результатами. Последний подтверждённый результат карточки берётся
из её собственного audit trail; отсутствие события видно как отсутствие
доказательства. Внешние Broker/Orchestra и другие runtime без точного Room ID
показаны отдельно и не прибавляются к статусам карточек Room. Число внешних
активных потоков выводится только для свежей, атрибутированной проверки.
Если проверка старше часа, текущий счёт объявляется неизвестным.

Для блокера выводится дословный открытый вопрос, следующий шаг и поля
рекомендации/вариантов/последствий. В нынешней Room схеме последние три поля
не структурированы, поэтому страница честно показывает, что они не
зафиксированы. Шестичасовой контроль вычисляется только для открытого
вопроса. Доставка напоминаний ведётся отдельно от страницы; сама страница
не отправляет сообщения.

Для внешнего исполнения проверяющий dot публикует через существующий
`room_post` в `main` сообщение `status=info`, `to=office-dashboard`, без
`task_id`. Сервер сохраняет реального OAuth actor. Тело начинается с
`OFFICE_RUNTIME_V1` и новой строки, затем JSON с `checked_at` в UTC и
`entries`: `project`, `thread_id` (UUID), `state` (`active`, `completed`,
`waiting`, `unknown`), `detail`. Перед публикацией dot проверяет runtime и
отсутствие дубля. Dashboard принимает только сообщения actor `dot`,
проверяет схему, время и дубликаты thread ID, читает последние 20 кандидатов.
Сводка старше часа не даёт текущего активного счётчика. Запись не создаёт
Room lease, не меняет карточки и не доказывает связь с ними. Для связи
нужен отдельный точный идентификатор; до этого покрытие остаётся неизвестным.

URL: `https://dima.veranda.my/office/hourly`. Для отката достаточно вернуть
предыдущий код dashboard; данные Room не меняются.

## Реализация

`office_hourly` — owner-only HTTP route; `load_report` выбирает ограниченный
набор событий из PostgreSQL, `build_report` группирует их в `HourlyReport` и
`HourlyCard`, `report_body` создаёт HTML. `status_of` задаёт отображение шести
статусов, `evidence_of` отделяет давнее или отсутствующее сообщение о
результате, `next_question_reminder` вычисляет следующий шестичасовой
контроль открытого вопроса для подписи на странице. `parse_runtime_snapshot`
проверяет атрибутированную сводку внешних runtime из Room messages, а
`latest_runtime_snapshot` выбирает самое позднее время проверки даже при
поздней доставке старого сообщения. `RuntimeSnapshot.is_fresh` ограничивает её актуальность; `RuntimeEntry`
сохраняет каждый источник как отдельное наблюдение без склейки с Room.
