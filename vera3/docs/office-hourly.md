# Часовой отчёт в Office dashboard

Страница `/office/hourly` использует существующую owner cookie авторизацию
дашборда. Она вычисляется из Room PostgreSQL при загрузке и автоматически
перезагружается каждые пять минут. Нового токена, публичного API, таблицы или
фоновой записи нет.

Единица учёта — `(room, task_id)`. Модель данных знает ровно шесть
пользовательских статусов, но страница показывает только четыре: «Новая / в
очереди», «В работе», «Блокер», «Ревью». «Готово» и «Отменена» из отчёта
исключены полностью: нет ни карточек, ни плиток, ни счётчиков, ни проектных
плиток, ни событий часа. Ничего не удаляется: `done` и `cancelled` остаются в
Room, история и события задач не меняются, модель по-прежнему возвращает эти
статусы. Страница не возобновляет задачи.
Живая аренда нужна, чтобы назвать карточку «В работе»; `open` не считается
исполнением. Шесть статусов вычисляет чистая функция `describe_status`
(`office_status.py`, без БД и I/O); сопоставление ниже. Свежесть и
«неизвестно» — отдельные поля, не статусы.

| Условие (по порядку приоритета) | Статус |
|---|---|
| raw `done` | Готово (в отчёт не выводится) |
| raw `cancelled` | Отменена (в отчёт не выводится) |
| открытый вопрос владельцу | Блокер, уверенность «подтверждён», `open_question = true` |
| последнее control-событие `review` или ответ владельца ждёт подтверждения | Ревью |
| control-событие `paused`, raw `blocked` / `paused` (`waiting` не блокер, см. ниже) | Блокер |
| живая аренда (holder и `lease_until` > now) | В работе |
| иначе (`open`, нет аренды, аренда истекла) | Новая / в очереди |

Пользовательских статусов ровно шесть; статуса «Ждёт / зависимость» нет.
Причина, зависимость и уверенность — отдельные поля `StatusInfo`, не
зависящие от статуса:
- `wait_reason` — `waiting_reason` строки (его ставит `room_task_wait`, аренда и
  статус при этом сохраняются, карточка остаётся «В работе»); для блокера
  без `waiting_reason` берётся причина из доказывающего события (см. ниже), а
  не `note` строки;
- `dependency` — `waiting_until`, пока срок не прошёл, и `depends_on`, если
  задача заблокирована либо ждёт;
- `blocker_confidence` ∈ «подтверждён» / «не подтверждён» / пусто (не блокер).

На странице рядом со статусом: «Блокер · подтверждён» или «Блокер · не
подтверждён»; плитка «Блокер» считает все карточки со статусом «Блокер».
Причина и зависимость выводятся на любой карточке, где они заданы. «Следующее
действие» (`next_action`) показывается на каждой карточке, в том числе у
блокера без вопроса; панель вопроса появляется только при открытом вопросе.

Правило доказательства блокера (`blocker_confidence_of`,
`BLOCKER_EVIDENCE_KINDS`): «подтверждён» только при явном свидетельстве.
1. Открытый вопрос по задаче.
2. Либо последнее control-событие задачи с непустой причиной от известного
   актора, в одной из форм, которые пишет `vera_shared.room`:
   - `released` с `data.status = "blocked"` и причиной в `text` (`room_task_release`;
     держатель аренды при этом очищается);
   - `waiting` с причиной в `text` (`room_task_wait`);
   - `blocked` (переход при `room_task_update(status="blocked")`): `text` у него
     пуст, причина лежит в `progress`-событии, которое тот же вызов пишет в той
     же транзакции (`data.status = "blocked"`, `text` = заметка). `bound_reason_of`
     берёт причину только из события, которое следует сразу за переходом по id
     задачи, с тем же `agent`, `fencing_token` и `at` (допуск
     `BOUND_AT_TOLERANCE`). Изменяемые поля строки (`note`,
     `last_progress_text`) не используются: поздний прогресс или старая заметка
     не должны подтверждать блокер. `load_report` для этого дочитывает по одному
     следующему событию для каждого `blocked`-перехода.

Известный актор: текущий держатель, `created_by`, `owner`, `responsible` или
`data.holder`; если известных акторов нет совсем, достаточно непустого автора.
Иначе «не подтверждён»: сам raw `blocked`, `paused` или `waiting` без
причины или с чужим автором подтверждением не считается.
Ограничения данных: `room_tasks` хранит только текущего держателя, а событие
`released` не записывает предыдущего, поэтому блокер, снятый с задачи другим
исполнителем, чем создатель или ответственный, остаётся «не подтверждён».
Control-запрос учитывает и события `waiting`.
Открытый вопрос при задаче, которая иначе «в работе», даёт «Блокер» и всегда
виден в поле `open_question` (блок вопроса на карточке), он не скрывается.

Правило свежести: `last_signal_at` — позднее из `last_progress_at` строки и
времени последнего результата (`done` или валидный `progress`) из audit trail;
в строке задачи нет отметок захвата и heartbeat аренды, поэтому они в сигнал не
входят. `freshness_of` даёт `fresh` — сигнал не старше `FRESH_MAX_AGE` (1 час,
включительно), `stale` — старше, `unknown` — сигнала нет совсем.
Метка «На проверке» заменена на «Ревью»; `paused` раньше показывался как
очередь, теперь это «Блокер · не подтверждён». `status_info_of` в
`office_hourly_service.py` собирает вход `describe_status` из строки задачи,
вопроса и control-события.

Часовая дельта включает только события выделенного метода `room_task_progress`
с текстом результата, созданные в точном интервале `[as_of - 1h, as_of]` для
видимых незакрытых задач. Признак метода — `next_checkpoint_seconds` в audit
data. Общий `room_task_update` тоже пишет `progress`, но может означать лишь
заметку или смену статуса и поэтому не попадает в результаты часа.
`metadata_updated`, `claimed`, `heartbeat` и изменение `updated_at` не
являются результатами. Последний подтверждённый результат карточки берётся
из её собственного audit trail; отсутствие события видно как отсутствие
доказательства. Внешние Broker/Orchestra и другие runtime без точного Room ID
показаны отдельно и не прибавляются к статусам карточек Room. Число внешних
активных потоков выводится только для свежей, атрибутированной проверки.
Если проверка старше часа, текущий счёт объявляется неизвестным.
Плитки проектов подписывают `Room lease` и внешнее выполнение отдельно;
отсутствие проверки проекта отображается как «не проверено», не как ноль.

Для блокера выводится дословный открытый вопрос, следующий шаг и поля
рекомендации/вариантов/последствий. В нынешней Room схеме последние три поля
не структурированы, поэтому страница честно показывает, что они не
зафиксированы. Шестичасовой контроль вычисляется только для открытого
вопроса. Доставка напоминаний ведётся отдельно от страницы; сама страница
не отправляет сообщения.

Для внешнего исполнения проверяющий dot публикует через существующий
`room_post` в `main` сообщение `status=info`, `to=office-dashboard`, без
`task_id`. Сервер сохраняет реального OAuth actor. Тело начинается с
`OFFICE_RUNTIME_V1` и новой строки, затем JSON с `checked_at` в UTC и
`entries`: `project`, `thread_id` (UUID), `state` (`active`, `completed`,
`waiting`, `unknown`), `detail`. Перед публикацией dot проверяет runtime и
отсутствие дубля. Dashboard принимает только сообщения actor `dot`,
проверяет схему, время и дубликаты thread ID, читает последние 20 кандидатов.
Сводка старше часа не даёт текущего активного счётчика. Запись не создаёт
Room lease, не меняет карточки и не доказывает связь с ними. Для связи
нужен отдельный точный идентификатор; до этого покрытие остаётся неизвестным.

URL: `https://dima.veranda.my/office/hourly`. Для отката достаточно вернуть
предыдущий код dashboard; данные Room не меняются.

## Реализация

`office_hourly` — owner-only HTTP route; `load_report` выбирает ограниченный
набор событий из PostgreSQL, `build_report` группирует их в `HourlyReport` и
`HourlyCard`, `report_body` создаёт HTML. `status_of` задаёт отображение шести
статусов, `evidence_of` отделяет давнее или отсутствующее сообщение о
результате, `next_question_reminder` вычисляет следующий шестичасовой
контроль открытого вопроса для подписи на странице. `parse_runtime_snapshot`
проверяет атрибутированную сводку внешних runtime из Room messages, а
`latest_runtime_snapshot` выбирает самое позднее время проверки даже при
поздней доставке старого сообщения. `RuntimeSnapshot.is_fresh` ограничивает её актуальность; `RuntimeEntry`
сохраняет каждый источник как отдельное наблюдение без склейки с Room.

## Детали карточки (Ф2)

Каждая карточка несёт `CardDetails` (`HourlyCard.details`), собранный только из уже
читаемых таблиц Room: ни таблиц, ни токенов, ни записи. Готовые и отменённые
по-прежнему исключены из отчёта; детали строятся лишь для видимых карточек.

- Артефакт: `artifact_of` берёт последнее «событие результата» карточки (то же
  определение, что в `load_report`: `done` либо `progress` с текстом и
  `next_checkpoint_seconds`). Текст проходит `safe_text` (редакция секретов
  `redact_view`, усечение до 280 символов; HTML-экранирует рендер). Ссылки
  `ref_links`: только `kind`/`ref`, ссылкой (`<a>`) становится лишь `url` со схемой
  http/https. События результата сами refs не несут, поэтому берутся refs задачи
  (`RoomTaskRow.refs`); если в `data.refs` события они есть, приоритет у них.
  Модель `Artifact`, `RefLink`.
- Исполнитель: `executor_of` — живой `lease_holder`, иначе `responsible`, иначе
  `owner`; подпись говорит, какое из трёх (`Executor.label`).
- Следующий шаг: `next_action` через `safe_text`.
- Очередь и зависимости: `dependencies_of` даёт для каждого id из `depends_on`
  текущий пользовательский статус из `describe_status` (`DependencyState`);
  неизвестный id — «не найдена». `waiting_until` и `waiting_reason` выводятся из
  `StatusInfo.dependency` и `StatusInfo.wait_reason` без дублирования логики.
- За час: `delta_of` собирает `HourlyDelta` — переходы статуса за `[as_of - 1h, as_of]`
  по control-событиям (`TRANSITION_KINDS`, включая `cancelled`) и число новых
  результатов окна; без того и другого рендер пишет «без изменений».
  Единственный дополнительный запрос — `load_transitions` (один пакетный select
  по `kind` и `at`, без N+1). `build_details` собирает всё вместе, `details_html`
  (`office_card_view.py`) рисует блок.

### Ожидание не равно блокеру

Ожидание решения или проверки (`room_task_wait`: `waiting_reason`, `waiting_until`,
control-событие `waiting`, raw `waiting`) само по себе не даёт «Блокер»: истёкшая
аренда и давняя причина не доказывают текущий блок. Блокер остаётся только при
открытом вопросе, raw `blocked`/`paused` либо control `paused`. Шесть статусов не
меняются; седьмого статуса «Ожидание» нет. Выбранное сопоставление (наименее
неверное): ожидающая задача получает статус по аренде, как обычная, то есть живая
аренда даёт «В работе», иначе «Новая / в очереди» (никогда не «Блокер» и не
выдуманная «В работе» без аренды). Отличие несут отдельные поля `StatusInfo`:
`waiting`, точный `wait_reason`, `decision_owner`, `wait_freshness`
(fresh/stale/unknown по `waiting_until` или времени события `waiting`, функция
`wait_freshness_of`) и существующие `freshness`, `blocker_confidence` (у
ожидания пусто). `decision_owner_of` берёт «кто действует» только из явных полей
события (только `data.decision_owner`); ни ответственный, ни автор
события `waiting`, ни адресат не подставляются, потому что это исполнитель, а не
решающий. Нынешний `room_task_wait` таких полей не пишет, поэтому до их появления
поле пусто, а страница пишет «неизвестно». Открытый вопрос для Codex: нужен ли
отдельный явный способ указать решающего в `room_task_wait`.

Состояние ожидания берётся только из авторитетных полей строки: `waiting_reason`,
`waiting_until` в будущем либо raw `waiting`. Одно лишь последнее control-событие
`waiting` ожидание не включает: `room_task_progress` и `room_task_update` очищают
поля строки, и снятое ожидание не воскресает из журнала. Событие даёт только время
для `wait_freshness_of`.

`details_by_task` группирует переходы и результаты по задачам один раз и собирает
`CardDetails` для всех видимых карточек; чистые помощники часового отчёта
(`status_info_of`, `evidence_of`, `next_question_reminder`) живут в
`office_hourly_status.py`, а `office_hourly_service.py` реэкспортирует их.
