# Memory ceilings — замеры

Раздел «Memory ceilings (`mem_limit`)» в [`deploy-ops.md`](deploy-ops.md)
описывает, зачем лимиты нужны. Здесь — откуда взяты числа.

## Замеренный пол

RSS питона сразу после импорта точки входа сервиса (той, что стоит в `CMD`
его Dockerfile), python3.12, те же версии зависимостей:

| Сервис | Импорт, МБ | `mem_limit` | Кратность |
|---|---|---|---|
| bot-telegram | 169 | 448m | 2.7× |
| ingestor-telegram | 106 | 384m | 3.6× |
| ingestor-instagram | 82 | 256m | 3.1× |
| dashboard | 75 | 256m | 3.4× |
| gateway | 68 | 256m | 3.8× |
| brain-search | 66 | 320m | 4.8× |
| ingestor-slack | 59 | 192m | 3.3× |
| ingestor-gmail | 59 | 192m | 3.3× |
| ingestor-trello | 51 | 160m | 3.1× |
| media-worker | 50 | 384m | 7.7× |
| brain-triage | 50 | 256m | 5.1× |

`postgres` (768m) и `prune` (64m) в таблице нет: это чужие образы, не наш
питон, и их потолки считаются по-другому (`shared_buffers` у первого,
`docker:cli` у второго).

## Зачем это было нужно

Лимиты появились в том же ревью как **оценки** — снять `docker stats` с живого
бокса было нельзя. Одна из оценок оказалась аварией:

**bot-telegram стоял на `160m` при импорте в 169 МБ.** Контейнер ушёл бы в OOM
ещё до первого апдейта и зациклился бы на `restart: unless-stopped` — то есть
деплой той ветки положил бы бота насмерть, а не просто «иногда тесновато».

Виноват не наш код: `import aiogram` один стоит 165 МБ из 169. aiogram 3.31 на
импорте строит ~1115 модулей pydantic-моделей под весь Bot API. Сжать это
нечем — только потолком.

По той же причине подняты `gateway` (192→256) и `ingestor-instagram`
(192→256): 2.8× и 2.3× от импорта — это не запас, а второй такой же случай
через одну зависимость. Остальные восемь лимитов замер прошли.

## Что этот замер НЕ говорит

Импорт — это **пол**, а не рабочий RSS. Сверху ложатся пул SQLAlchemy,
буферы httpx и пик обработки — поэтому лимит берётся как импорт × ~2.5-3, и это
по-прежнему потолок, а не замер потребления. Замер закрывает только один
класс ошибок — лимит ниже того, без чего процесс вообще не стартует.

Первый же спокойный час на проде по-прежнему: `docker stats --no-stream` и
подтянуть вниз по факту. Занижение опаснее завышения: слишком тесный
лимит убивает здоровый контейнер, то есть ровно ту аварию, которую предотвращает.

## Охрана инварианта

`tests/unit/test_compose_mem_limits.py` держит правило **потолок ≥ 2× импорта**
с таблицей полов выше и отдельно проверяет, что лимит есть у КАЖДОГО
сервиса из compose (сервис без лимита отдаёт выбор жертвы OOM-killer'у,
включая чужие стеки на том же боксе). Сам замер в тесте не повторяется: он
потребовал бы всех зависимостей одиннадцати сервисов и их обязательных env.

Тест проверен поломкой: возврат bot-telegram на 160m его валит с текстом
«mem_limit 160m при импорте 169 МБ — нужно минимум 338m».

## Повторить замер

Суммарный потолок сейчас **4.8 ГиБ** (4.6 без выключенного профилем
`ingestor-instagram`) на боксе в 3.7 ГиБ — переподписка сознательная, см.
комментарий в шапке `infra/docker-compose.yml`.

Переснять пол для одного сервиса (в окружении, где есть его зависимости):

```bash
python3 - <<'PY'
import importlib, sys
def rss():
    for line in open("/proc/self/status"):
        if line.startswith("VmRSS:"):
            return int(line.split()[1]) / 1024
before = rss()
importlib.import_module(sys.argv[1] if len(sys.argv) > 1 else "bot_telegram.bot")
print(f"{before:.1f} -> {rss():.1f} MB")
PY
```

После апгрейда тяжёлой зависимости (aiogram, telethon, sqlalchemy) пол может
уехать вверх — тогда обновить `IMPORT_FLOOR_MB` в тесте и таблицу выше.
