# Общая работа dot, Vera и существующего Claude

Это рабочий протокол поверх существующих Room/Office API. Ответственный ведёт
один канонический `(room, task_id)` от поручения до проверенного результата и
подтверждённой отправки. Документ не меняет платформенные инструкции dot,
полномочия агентов, approval gates, бюджеты или расписания.

## Ответственный и исполнитель

- `responsible` содержит одного ответственного за итог, например `dot`.
  Это метка координации, а не право действовать от имени владельца.
- Один текущий исполнитель определяется живой арендой и
  `(lease_holder, holder_session, fencing_token)`. Перед началом работы читать
  актуальную задачу, историю, вопросы и последнее решение владельца.
- Ответственный может сам исполнять задачу. Для небольшого ревью передавать
  конкретный diff/артефакт, а не весь разговор и владение основной задачей.
  Reviewer не становится вторым автором тех же файлов.
- При настоящей смене исполнителя использовать `handoff.offer` /
  `handoff.accept`: до приёма работает отправитель, после приёма старый
  fencing-токен недействителен. `ack` сообщения не означает приём исполнения.
- Занятая задача не порождает второго исполнителя или новый task_id. Читать
  состояние существующего, фиксировать следующий шаг, ждать разрешённого handoff.

Lease защищает между именами агентов. API не проверяет единственность runtime
одного имени: `holder_session` — аудит, а не отдельный capability. Два runtime
с одним principal могут использовать тот же токен. Поэтому ответственный
сверяет текущую сессию и запрещает параллельных авторов в рамках этого протокола;
документ не заявляет новой защиты от такого столкновения.

## Ссылки вместо пересказов

В `refs` сохранять только указатели с существующим kind `source`/`url`;
текст по ним не становится доверенным автоматически. Минимальный пакет:

| Указатель | Что проверить при чтении |
|---|---|
| `task_ref` | точные room, task_id, текущая ревизия/событие журнала |
| `request_ref` | numeric Room id и строковый message_id исходного поручения; для внешнего источника — неизменяемый origin и client_task_id |
| `owner_decision_ref` | последнее применимое решение владельца, его источник, точная область действия; известная пауза или отмена имеет приоритет |
| `execution_ref` | агент, сессия, fencing_token и событие claim/accept |
| `result_ref` | numeric id сообщения, его message_id, task_id, автор и ссылка на конкретный артефакт/commit |
| `verification_ref` | независимый reviewer и результат проверки именно этого артефакта/SHA, реальные тесты и непроверенные границы |
| `delivery_ref` | канал, получатель, ссылка на отправленный результат и реальный receipt; неизвестный исход остаётся неизвестным |

Это имена полей рабочего пакета в тексте сообщения, не новая JSON-схема API.
Например: `result_ref = room main / id 123 / message_id result-T1-v1 / task T1`.
Числовой `id` читается через `room_message_get`; строковый `message_id`
используется в `in_reply_to` и для идемпотентного повтора.

Читать полный результат через `room_message_get(id, room, task_id)`.
Необязательный `task_id` проверяется в `get_message`: чужая задача или сообщение
без задачи возвращается как не найденное. Без аргумента старое чтение сохраняется.
Проверка не подтверждает автора, тип результата, артефакт или факт отправки:
их ответственный сверяет отдельно. Похожий заголовок/текст не заменяет совпадение ID.

## Решения, пауза и повтор

1. Повтор исходного события — тот же client_task_id/message_id и тот же payload.
   Проверить сохранённый результат, не отправлять заново с новым ID. Конфликт
   содержимого требует разбирательства, а не нового идентификатора ради обхода.
2. Уже данное решение дочитать по source ref или последнему ответу того же qid,
   применить в его области и подтвердить через штатный `questions.ack`.
   Не задавать тот же вопрос заново. Изменённый ответ владельца сохраняется в истории.
3. «Погоди», пауза или отмена останавливает зависимую работу, новые передачи и
   отправки. Не считать поздний прогресс разрешением продолжить. Отразить решение
   штатными owner actions/вопросом, если текущий principal это позволяет;
   агент не выдаёт свою запись за OWNER и не снимает owner block.
4. При гонке с паузой/отменой повторно проверить состояние перед внешним эффектом.
   Room не может отозвать уже выполненную внешнюю отправку; такой исход сверить
   по receipt и сообщить ответственному, не обещая атомарности между системами.

## Точечное ревью Claude

Использовать существующий разрешённый поток, одну ограниченную просьбу с
task/request/result refs, base/head SHA и вопросом ревью. При известном
исчерпании квоты не вызывать, не опрашивать модель пробными запросами и не
переключать аккаунт/маршрут ради обхода. При сообщении о лимите после запроса
не повторять. Сохранить точную ссылку отказа, отметить «Claude review не выполнено».
Если независимое ревью обязательно, получить его у другого разрешённого
независимого рецензента либо оставить этот gate открытым. Квота не снимает gates.

## Проверенный результат и подтверждённая отправка

Готовый артефакт, Room `done`, отправка и получение — разные факты.
Ответственный проверяет result_ref и verification_ref до финального заявления,
затем проверяет receipt именно нужного канала/получателя. Локальные тесты не
доказывают CI или деплой; Room-публикация не доказывает доставку владельцу.

- `dispatch-<task_id>` + адресный `ack` — квитанция приёма dispatch-сообщения,
  не результат и не доказательство отправки владельцу.
- Голосовой путь: `delivery.state=sent` и message_id, а для результата исполнителя
  `source.result_message_id`/`result_sent_at` и `help_state=closed`;
  `claimed`, пустой message_id, `result_pending`/`result_unknown` не финальная квитанция.
  Неизвестный исход не повторять автоматически.
- Office `mark_delivered` / delivered_revision означает, что источник подтвердил
  ревизию. API не проверяет внешнюю отправку пользователю. Нужен отдельный receipt
  от источника; монотонная отметка сама по себе его не создаёт.
- ChatGPT/dot receipt — утверждение доверенного транспорта/ответственного.
  Vera не может независимо прочитать закрытый чат. Указывать эту границу.

Если результат готов, но receipt отсутствует: «результат проверен, отправка не
подтверждена», со следующим действием в той же задаче. Не переписывать Room
`done` ради нового статуса: это критерий итогового отчёта, не миграция state machine.
Задача подготовки PR может завершиться проверенным PR и подтверждённым handback;
это не означает merge/deploy, если они не разрешены.

## Воспроизводимые проверки

Из корня: `python -m pytest vera3/tests/unit/test_mcp_room_tools.py
vera3/tests/unit/test_office_dispatch.py vera3/tests/unit/test_office_intake.py
vera3/tests/unit/test_room_handoff.py vera3/tests/unit/test_room_owner_pause.py
vera3/tests/unit/test_room_task_cancel.py vera3/tests/unit/test_room_questions.py
vera3/tests/unit/test_voice_result_delivery.py -q` (одна строка).

| Сценарий | Проверяемое ожидание и существующий тест |
|---|---|
| Повтор события | прежняя задача, без нового поста: `test_same_payload_returns_existing_task_without_duplicates` |
| Исполнитель занят | lease не отбирается: `test_other_project_and_held_lease_are_skipped`; после accept старый токен отклоняется: `test_accept_moves_lease_bumps_token_and_old_token_is_stale` |
| Пауза/отмена владельца | штатные тесты `test_room_owner_pause.py`, `test_room_task_cancel.py`; новая работа запрещена, историю сохраняем |
| Уже данное решение | дубль ответа не пишет событие, изменённый ответ сохраняется: `test_duplicate_answer_is_noop_and_edit_keeps_history` |
| Неверный result ID | чужая/непривязанная задача отклоняется: `test_full_get_rejects_result_from_another_or_unbound_task`; неверная комната/несуществующий ID — `test_bound_full_get_keeps_room_and_missing_id_boundaries` |
| Лимит Claude | ручной dry-run: известный отказ с ref → 0 новых запросов, review unavailable; восстановление квоты нельзя выдумывать |
| Нет доказательства отправки | `test_no_receipt_means_not_closed`, `test_crash_after_send_is_unknown_and_never_resent`; чужой ack не delivery: `test_result_receipt_and_foreign_acks_are_not_delivery_receipt` |

Unit-набор использует SQLite; Telegram/LLM в тестах заменены заглушками.
Он проверяет кодовые границы, не живую доставку, квоту или весь человеческий
протокол. PostgreSQL-сценарии — отдельные `test_dispatch_receipt_pg.py`,
`test_office_intake_pg.py`, `test_room_pg.py`; результат их запуска указывать отдельно.

Основа подхода: [Anthropic — when to fold subagents into the main loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop):
сохранять общий контекст у ответственного, передавать узкие проверяемые артефакты
и сравнивать end-to-end сценарии. Независимое ревью и tool-level gates сохраняются.
